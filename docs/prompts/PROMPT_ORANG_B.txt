# BAGIAN 2 — M-05 Uji Konsisten

## PRD

**Tujuan.** Menandai catatan pemeriksaan yang tidak sejalan dengan catatan lain di rekam medis yang sama (modus Manipulasi Hasil Pemeriksaan, UC-2), tanpa menilai mana yang benar secara klinis.

**User story.** Sebagai verifikator, saya ingin melihat catatan pemeriksaan yang tidak sejalan dengan catatan lain, beserta kedua kutipannya berdampingan, supaya tahu bagian mana yang perlu dikonfirmasi ke faskes.

**Kriteria penerimaan:**
1. Klaim profil `EXAM_MANIPULATION` (seed demo) dan skenario `UC2_EXAM_MANIPULATION` / `MULTI_UPCODING_EXAM` (dataset LLM) mendapat ≥ 1 finding `CONSISTENCY` setelah dianalisis.
2. Profil lain tidak mendapat finding `CONSISTENCY`:
   - `NORMAL_*`, `GENUINE_*`, `SHOCK_UPCODING`, `RESP_FAILURE_UPCODING`, `SHOCK_NONSTANDARD`, `CLONING`;
   - skenario dataset LLM selain yang disebut di poin 1.
3. Finding kontradiksi menampilkan dua kutipan: dokumen yang dicurigai (`documentId`) dan dokumen pembanding (`relatedDocumentId`).
4. Analisis ulang tidak menggandakan finding.

## TRD

### Kosakata

Tambahkan di `clinical-vocabulary.ts`:

```ts
/** Maps an extracted finding name to its canonical term for comparison across documents. */
export function toCanonicalFinding(name: string): string
```

Langkahnya:
1. Ubah ke huruf kecil, trim, dan satukan spasi.
2. Jika nama persis ada di `TERM_SYNONYMS`, kembalikan istilah kanoniknya.
3. Jika tidak, ambil istilah terpanjang dari `CANONICAL_TERMS.findings` yang terkandung di nama.
4. Jika tidak ada yang cocok, kembalikan nama yang sudah dinormalisasi.

### Aturan (`src/domain/analysis/consistency-test.ts`)

Fungsi utama: `findInconsistencies(claim: ClaimEvidence): Inconsistency[]`, diurutkan dari `strength` tertinggi.

- **Waktu butir** = `observedAt` / `givenAt` / `performedAt` jika ada, selain itu `recordedAt` dokumennya.
- **Dokumen klaim** = `EXAM_NOTE` dan `MEDICAL_RESUME`, yaitu dokumen yang menentukan tingkat keparahan.
- **Masa rawat** = `admittedAt` 00:00 sampai akhir hari `dischargedAt`, waktu `+07:00`. Kolom tanggal disimpan sebagai UTC tengah malam, jadi bentuk batasnya dari `toISOString().slice(0, 10)` + `T00:00:00+07:00`.

| Kode | Aturan | `strength` | `documentId` | `relatedDocumentId` | Kutipan |
|---|---|---|---|---|---|
| `CONTRADICTED_FINDING` | Temuan `isPresent: true` di dokumen klaim, dan `DAILY_NOTE` mencatat temuan kanonik yang sama dengan `isPresent: false`, dengan selisih waktu ≤ 24 jam | 0.9 | Dokumen klaim | Catatan harian | Dua `QUOTE` |
| `FINDING_WITHOUT_ACTION` | Temuan `isPresent: true` **di dokumen klaim** yang ada di `FINDING_REQUIRED_ACTIONS`, tetapi tidak satu pun obat atau tindakan di seluruh dokumen yang namanya memuat salah satu tindakan wajib | 0.7 | Dokumen sebutan pertama | `null` | Satu `QUOTE` |
| `IMPLAUSIBLE_TIME` | `recordedAt` dokumen atau waktu butir di luar masa rawat | 0.6 | Dokumen itu | `null` | Satu `QUOTE`: kutipan butir, atau kalimat pertama dokumen |

```ts
export const FINDING_REQUIRED_ACTIONS: Readonly<Record<string, readonly string[]>> = {
  'sesak napas': ['oksigen'],
  'akral dingin': ['resusitasi cairan', 'ringer laktat'],
};
```

- Jangan menambahkan `syok` ke tabel ini. Diagnosis syok tanpa bukti adalah wilayah Uji Ada.
- `FINDING_WITHOUT_ACTION` hanya melihat dokumen klaim, karena catatan harian profil `RESP_FAILURE_UPCODING` di seed demo menulis "sesak berkurang" tanpa oksigen, dan itu bukan modus yang dicari uji ini.

**Deduplikasi:** satu finding per nama temuan kanonik untuk dua aturan pertama (ambil pasangan dengan selisih waktu terkecil), dan satu per dokumen untuk `IMPLAUSIBLE_TIME`.

**Contoh `summary`:** *Catatan pemeriksaan 3 Sep menulis "sesak napas", tetapi catatan harian 4 Sep menulis sebaliknya.* Label tipe dokumen dalam bahasa Indonesia dibuat sebagai map kecil di domain.

### Use case dan wiring

- **`RunConsistencyTestUseCase.execute(claim)`**, pola sama dengan `RunExistenceTestUseCase`:
  - `testType: 'CONSISTENCY'`, `strength` 2 desimal, `citations` berisi `QUOTE`;
  - `diagnosisId`, `relatedClaimId`, `similarity`, dan `tariffGap` bernilai `null`;
  - simpan dengan `replaceFindings(claimId, 'CONSISTENCY', findings)`, termasuk array kosong.
- Panggil di `EvaluateClaimUseCase.execute` setelah Uji Ada, **sebelum** `findFindingSignals`. Daftarkan di `analysis.module.ts` dengan pola `useFactory`.
- Tambahkan paragraf **Uji Konsisten (M-05) rules** di `docs/contracts/README.md` setelah aturan Uji Ada.

### Verifikasi

1. Seed demo (`npm run seed`), login, lalu analisis beberapa klaim tiap profil dari Antrean Klaim.
2. Cek kriteria 1–4 lewat query. Pemetaan profil ada di `scripts/synthetic/demo-claims.ts`; untuk mengenali profil di database, pakai `injected_case` dan diagnosis.
3. Buka Kartu Klaim satu klaim `EXAM_MANIPULATION`: panel Uji Konsisten menampilkan dua kutipan dengan tautan ke dokumennya.
4. Jika ada profil normal yang tertandai, perbaiki aturan atau template yang benar-benar keliru secara klinis. Jangan menambah pengecualian per klaim.

# BAGIAN 3 — M-06 Uji Bukan Salinan

## PRD

**Tujuan.** Mengenali rekam medis yang disalin dari pasien lain (modus Cloning, UC-3) dengan mengukur kemiripan teks antar klaim, lalu menyorot kalimat yang identik. Uji ini tidak memakai LLM.

**User story.** Sebagai verifikator, saya ingin melihat klaim lain yang isinya hampir sama beserta kalimat identiknya, supaya bisa mengenali pola salinan dan mengeskalasi klusternya.

**Kriteria penerimaan:**
1. Setiap klaim kloning (Bagian 4) yang dianalisis mendapat ≥ 1 finding `SIMILARITY` yang menunjuk klaim lain di klusternya.
2. Klaim non-kloning tidak mendapat finding `SIMILARITY` dengan ambang default, **walaupun seed demo memakai template yang mirip antar klaim**.
3. Klaim dari pasien yang sama tidak pernah dibandingkan.
4. Analisis ulang tidak menggandakan finding dan tidak melanggar unique `(claimId, relatedClaimId, testType)`.
5. Kartu Klaim klaim kloning menampilkan persentase kemiripan, tautan ke klaim mirip, dan minimal satu kalimat identik yang disorot.

## TRD

### Masalah utama yang harus diatasi

Seed demo dibuat dari template, sehingga banyak kalimat sama di semua klaim dengan penyakit yang sama. Contohnya resep DBD selalu "Infus RL 20 tetes/menit, parasetamol 3 x 500 mg per oral.", dan resume selalu "Diagnosis utama: ...". Membandingkan kata saja akan membuat semua klaim tampak tersalin.

Desain di bawah mengatasinya dengan IDF (kalimat yang muncul di banyak klaim diberi bobot kecil) dan dengan mempertahankan angka (klaim normal punya angka tanda vital acak, sedangkan klon menyalin angkanya juga).

### Konfigurasi

- Tambahkan `SIMILARITY_THRESHOLD: z.coerce.number().min(0).max(1).default(0.85)` di `env.schema.ts` dan `.env.example`.
- Use case menerima ambang lewat constructor. Factory di module membaca `ConfigService<Env, true>`.

### Data pembanding (repository)

Tambahkan di `AnalysisRepository`:

```ts
/** Other claims that share a primary diagnosis with the given claim, excluding the same patient. */
abstract findSimilarityCandidates(claim: ClaimEvidence): Promise<SimilarityCandidate[]>;
// SimilarityCandidate = { claimId, claimNo, patientId, documents: { id, type, content }[] }
```

- Kandidat tidak perlu sudah diekstraksi, karena uji ini membaca `content` mentah.
- Batasi ke klaim dengan diagnosis utama yang sama, supaya korpus kecil dan relevan.

### Kemiripan (`src/domain/analysis/similarity-test.ts`)

**Teks per klaim:** gabungan `content` semua dokumen, diurutkan per tipe lalu waktu.

**Token:**
- huruf kecil;
- karakter selain huruf dan angka diganti spasi;
- angka **dipertahankan**, dan koma desimal dinormalkan.

**Fitur:** shingle 3 kata (word 3-gram).

**Vektor:**
- TF-IDF atas korpus = klaim yang dianalisis + semua kandidat;
- `idf = ln((1 + N) / (1 + df)) + 1`;
- skor = cosine.

**Kalimat identik:**
- Pecah per kalimat (`.`, `!`, `?`, atau baris baru), lalu bandingkan setelah huruf kecil dan penyatuan spasi.
- Ambil kalimat sama minimal 25 karakter yang muncul di **≤ 10% klaim korpus**, supaya boilerplate template tidak disorot.
- Maksimal 3 per pasangan.
- `text` memakai kalimat asli milik klaim yang dianalisis. `documentId` adalah dokumen asal kalimat itu di klaim yang dianalisis, `relatedDocumentId` dokumen pasangannya.

**Fungsi:**

```ts
/** Every candidate scored against the claim. Unfiltered, for calibration. */
export function scoreSimilarClaims(claim: ClaimEvidence, candidates: SimilarityCandidate[]): SimilarClaimMatch[];
/** Matches at or above the threshold, strongest first. */
export function findSimilarClaims(claim, candidates, threshold): SimilarClaimMatch[];
// SimilarClaimMatch = { relatedClaimId, relatedClaimNo, similarity, documentId, relatedDocumentId, identicalTexts[] }
```

`documentId` dan `relatedDocumentId` menunjuk `MEDICAL_RESUME` masing-masing klaim. Jika tidak ada, pakai dokumen pertama klaim itu.

### Use case `RunSimilarityTestUseCase`

```ts
constructor(analysisRepository: AnalysisRepository, threshold: number)
execute(claim: ClaimEvidence): Promise<void>
```

1. Ambil kandidat, lalu jalankan `findSimilarClaims`.
2. Ambil maksimal 5 dengan kemiripan tertinggi.
3. Petakan ke `NewFinding`:

   | Field | Nilai |
   |---|---|
   | `testType` | `'SIMILARITY'` |
   | `strength`, `similarity` | Skor, 2 desimal |
   | `relatedClaimId` | Klaim pasangan |
   | `documentId`, `relatedDocumentId` | Seperti di atas |
   | `citations` | `IDENTICAL_TEXT` |
   | `diagnosisId`, `tariffGap` | `null` |
   | `summary` | Contoh: *Rekam medis 96% mirip dengan klaim KLM-DEMO-0123 milik pasien lain.* |

4. Simpan dengan `replaceFindings(claimId, 'SIMILARITY', findings)`, termasuk array kosong.

Finding **hanya ditulis untuk klaim yang sedang dianalisis**. Klaim pasangan mendapat finding-nya sendiri saat ia dianalisis, supaya skor dan `analyzedAt`-nya tetap konsisten.

Panggil di `EvaluateClaimUseCase` setelah Uji Konsisten, sebelum `findFindingSignals`.

### Script kalibrasi `apps/api/scripts/similarity-report.ts`

- Read-only. Pola sama dengan script lain (Nest application context, `ConfigModule` dengan `validateEnv`).
- Untuk setiap klaim kloning dan sampel 50 klaim non-kloning, hitung `scoreSimilarClaims` terhadap kandidatnya, lalu cetak:
  - 10 skor tertinggi pasangan yang **bukan** keduanya kloning;
  - skor terendah pasangan **sesama** kluster kloning;
  - ambang aktif.
- Ambang yang baik berada di antara dua angka itu. Jika tumpang tindih, laporkan, jangan memaksakan angka.
- Tambahkan script `"eval:similarity": "tsx scripts/similarity-report.ts"` di `apps/api/package.json` dan alias root seperti script lain.
- Tambahkan paragraf **Uji Bukan Salinan (M-06) rules** di `docs/contracts/README.md`.

### Verifikasi

Kerjakan setelah Bagian 4 juga selesai, karena data kloning baru ada di sana:

1. `npm run eval:similarity` menunjukkan ambang default memisahkan kloning dari non-kloning. Jika tidak, sesuaikan default beserta alasannya.
2. Analisis satu klaim kloning dua kali: tanpa error unique constraint, dan jumlah finding sama.
3. Cek kriteria 1–3 dan 5 di Kartu Klaim dan lewat query.

# BAGIAN 4 — Kasus kloning di seed demo

# BAGIAN 5 — Script metrik presisi/recall (`apps/api/scripts/evaluate-detection.ts`)

Read-only. Hanya menghitung klaim yang sudah dianalisis (`analyzed_at` tidak null).

- **Per uji, di level klaim** (pemetaan uji ke modus di "Kontrak bersama"):
  - TP = punya modus terkait dan ≥ 1 finding uji itu;
  - FP = punya finding tetapi tidak punya modus itu;
  - FN = punya modus tetapi tidak ada finding.
  - Hitung presisi dan recall, dengan pembagi nol ditampilkan sebagai `-`.
- **Keseluruhan:** klaim dengan modus apa pun dibandingkan dengan klaim yang punya finding apa pun.
- **Estimasi selisih tarif:** total `potential_gap` pada klaim `UPCODING` yang tertandai `EXISTENCE`.
- **Catatan profil `SHOCK_NONSTANDARD` / skenario `UC4_FLAGGED_BUT_VALID`:** tampilkan terpisah, karena memang dirancang tertandai Uji Ada padahal wajar (dihitung FP).
- Tampilkan jumlah klaim dianalisis vs total, karena metrik hanya mewakili klaim yang sudah dianalisis.
- Judul output: "Estimasi berbasis data sintetis".
- Tambahkan script `"eval:detection"` di `apps/api/package.json` dan alias root.

# BAGIAN 6 — Fitur impor klaim massal (bulk import) dengan penyesuaian AI

## PRD

**Tujuan.** Pengguna bisa memasukkan banyak klaim sekaligus dari file. INTEGRA punya satu **format baku**. File yang sudah sesuai format langsung diproses. File yang belum sesuai (JSON dengan bentuk lain, CSV, atau teks) **disesuaikan oleh AI** ke format baku, lalu ditampilkan untuk dicek sebelum disimpan.

**User story.** Sebagai verifikator atau supervisor, saya ingin mengunggah file berisi banyak klaim, melihat pratinjau hasil pembacaannya, lalu mengimpornya, supaya klaim baru langsung masuk Antrean Klaim tanpa input satu per satu.

**Masuk lingkup:**
- format baku + file contoh yang bisa diunduh;
- unggah file `.json`, `.csv`, atau `.txt`;
- penyesuaian AI dengan konfirmasi biaya;
- pratinjau dengan status per klaim, lalu impor.

**Di luar lingkup:**
- file gambar atau PDF;
- impor kunci jawaban (`injected_case` selalu kosong untuk data impor);
- mengubah klaim yang sudah ada.

**Kriteria penerimaan:**
1. File contoh format baku terimpor tanpa memanggil AI.
2. File CSV dengan nama kolom berbeda bisa dipetakan AI ke format baku, ditandai "Disesuaikan AI" di pratinjau.
3. AI tidak pernah mengarang isi:
   - isi dokumen klinis harus ada di file asli;
   - field wajib yang tidak ada membuat klaim berstatus tidak valid, bukan diisi tebakan.
4. Klaim dengan `claimNo` yang sudah ada di database atau ganda di file berstatus duplikat dan tidak diimpor.
5. Klaim terimpor muncul di Antrean Klaim dengan status Menunggu keputusan dan belum dianalisis.
6. Sebelum AI dipanggil, pengguna mengonfirmasi lewat dialog yang menyebut perkiraan jumlah panggilan AI, sesuai pola konfirmasi analisis berbayar di `DESIGN.md`.

## TRD

### Format baku `integra-claims/v1`

Skema Zod di `apps/api/src/application/imports/claim-import.schema.ts`, yang juga menjadi sumber tipe:

```json
{
  "format": "integra-claims/v1",
  "claims": [
    {
      "claimNo": "KLM-2026-10-0001",
      "facility": { "code": "RS-SIM-001", "name": "...", "type": "A|B|C|D", "city": "..." },
      "patient": { "medicalRecordNo": "RM-...", "name": "...", "gender": "M|F", "birthDate": "YYYY-MM-DD" },
      "admittedAt": "YYYY-MM-DD",
      "dischargedAt": "YYYY-MM-DD",
      "inacbgCode": "A-4-14-II",
      "severityLevel": 1,
      "tariffAmount": 5730000,
      "diagnoses": [{ "icd10Code": "A91", "name": "...", "isPrimary": true }],
      "documents": [{ "type": "EXAM_NOTE|DAILY_NOTE|PRESCRIPTION|PROCEDURE|MEDICAL_RESUME", "recordedAt": "ISO 8601 +07:00", "content": "..." }]
    }
  ]
}
```

Aturan validasi:
- `dischargedAt` ≥ `admittedAt`;
- tepat satu diagnosis utama;
- minimal satu dokumen;
- `tariffAmount` > 0;
- `severityLevel` 1–3.

Buat contoh lengkap 2 klaim di `docs/contracts/claim-import.example.json`, salin juga ke `apps/web/public/templates/integra-claim-import.json` untuk diunduh, dan dokumentasikan di `docs/contracts/README.md`.

### Penyesuaian AI (`application/imports/`)

Alurnya:
1. Coba `JSON.parse` lalu skema format baku. Jika lolos, sumber = `CANONICAL`, tanpa AI.
2. Jika tidak lolos, sumber = `AI_NORMALIZED`. Pecah file menjadi potongan supaya satu klaim tidak terbelah:
   - **array JSON:** 5 record per potongan;
   - **CSV:** header diulang di setiap potongan, baris dengan nilai kolom pertama yang sama dijaga dalam satu potongan, sekitar 40 baris per potongan;
   - **teks:** dikelompokkan per paragraf, maksimal 12 KB per potongan.
3. Setiap potongan: `llm.generateStructured` dengan skema `{ claims: CanonicalClaim[], skipped: { reference: string, reason: string }[] }`, `temperature: 0`.
4. System prompt (bahasa Indonesia) mewajibkan:
   - hanya menyusun ulang;
   - menyalin isi dokumen kata per kata;
   - tidak mengarang nilai apa pun;
   - klaim dengan field wajib yang tidak ada dimasukkan ke `skipped` beserta alasannya;
   - memetakan tipe dokumen, tanggal, gender, dan tipe faskes ke enum dan format baku.
5. **Grounding** setelah AI: setiap `content` dokumen dan `claimNo` harus ada di teks potongan asli (setelah huruf kecil dan penyatuan spasi). Jika tidak, klaim berstatus `INVALID` dengan alasan "isi tidak ditemukan di file asli".
6. Batas:
   - file ≤ 2 MB dan ≤ 200 klaim;
   - potongan diproses lewat `LlmClient` (paralel sudah dibatasi `Semaphore`);
   - error LLM per potongan dilaporkan di pratinjau, tidak menggagalkan potongan lain;
   - `LlmConfigurationError` menghentikan pratinjau dengan `503`.

### API (controller tipis, use case di `application/imports/`, repository Prisma di infrastructure)

Kedua peran (`VERIFIER`, `SUPERVISOR`) boleh memakai fitur ini.

- **`POST /imports/claims/preview`**
  - Body: `{ fileName: string, content: string, allowAi: boolean }`.
  - Jika file tidak sesuai format baku dan `allowAi` false, balas `422 IMPORT_NEEDS_AI` dengan `{ estimatedAiCalls }`.
  - Jika berhasil, balas:
    ```
    { source: 'CANONICAL' | 'AI_NORMALIZED',
      claims: { index, claimNo | null, status: 'VALID' | 'INVALID' | 'DUPLICATE', issues: string[], claim: CanonicalClaim | null }[],
      summary: { valid, invalid, duplicate } }
    ```
    `DUPLICATE` berarti `claimNo` sudah ada di database atau ganda di file.
- **`POST /imports/claims`**
  - Body: `{ claims: CanonicalClaim[] }` (hanya yang `VALID`, maksimal 200).
  - Server memvalidasi ulang dengan skema Zod dan mengecek duplikat lagi.
  - Per klaim, dalam satu transaksi: faskes (berdasarkan `code`) dan pasien (berdasarkan `medicalRecordNo`) dibuat jika belum ada, **data yang sudah ada tidak ditimpa**; klaim dibuat dengan `status: PENDING`, `injectedCase: []`, dan dokumen dengan `extracted` null.
  - Balas `{ importedCount, skipped: { claimNo, reason }[] }`.
- **Batas body:** `main.ts` saat ini memakai batas body JSON default Express (100 KB). Naikkan menjadi 3 MB dengan `NestFactory.create<NestExpressApplication>` + `app.useBodyParser('json', { limit: '3mb' })`.
- Validasi body di controller dengan Zod di level application (`safeParse`, error → `400`). Jangan menduplikasi skema dengan class-validator.
